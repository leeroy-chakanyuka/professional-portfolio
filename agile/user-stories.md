## 1. Source and scope

The shared AquaLink portfolio identifies three main user groups: **households, borehole suppliers and administrators**. The table below summarises story themes documented by Faith Adams. It is a reference map, not a claim that these were the final approved Trello cards.

**Source:** [AquaLink user stories and sprint breakdown](https://github.com/FaithA965/FaithA965.github.io/blob/main/agile.md#2-user-stories-and-tasks).

## 2. Traceable user needs

| User | Need documented in team material | Related workstream |
|---|---|---|
| Household | Obtain reliable household access to water | Community research and connection requirements |
| Household | Request a connection to the AquaLink network | User and household information |
| Household | See subscriptions, payments and usage against the correct account | Entity relationships and backend design |
| Borehole owner | Register water supply and monitor availability | Supplier and borehole data model |
| Administrator | See information needed to manage community supply | Administration requirements and technical review |
| Platform user | Navigate a clear, consistent interface | Shared styling and usability |

## 3. Backend task breakdown — verification worksheet

When the Trello card details and my own records are available, each backend-related story should include:

| Field | Evidence to add |
|---|---|
| Trello card / story identifier | Exact card title and link |
| User need and acceptance criteria | Wording from the approved team story |
| Backend tasks assigned to me | Schema, endpoint or business-rule tasks that the records actually show |
| Implementation evidence | Commit, PR, ERD, API specification, test or screenshot |
| Status | Planned, in progress or completed — supported by evidence |
| Verification | Test outcome or reviewer feedback, if documented |

**Important:** Planned API functionality should not be described as delivered solely because it appears in a user story.
